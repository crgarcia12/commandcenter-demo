Data Storage & External Services

The only data store is a SQL Server database (ZavaBankDB) accessed directly via ADO.NET. The service queries two tables: CurrencyPairs (active currency pair definitions) and ExchangeRates (time-bound mid-rates). No external APIs, caches, or message brokers are used. The connection string is resolved at runtime from environment variables (DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD), falling back to web.config when those variables are absent.

Key Architectural Decisions

  • WCF SOAP over basicHttpBinding: The service contract is defined via [ServiceContract]/[OperationContract] attributes and exposed as a SOAP endpoint, targeting interoperability with .NET Framework clients.
  • Direct ADO.NET data access: No ORM is used; all database interactions are raw SqlCommand calls with parameterized queries, keeping the data layer minimal and dependency-free.
  • Environment-variable-first configuration: DbConfig checks environment variables before falling back to web.config, making the service container-friendly.

Core Business Workflows

ZavaCurrencyService is a single-service currency exchange utility that provides real-time exchange rate lookups and amount conversions for clients of the Zava Bank platform.

ZavaCurrencyService is a self-contained single-service application with no cross-service dependencies.

Primary Workflows

Workflow 1: Get Exchange Rate

A client requests the current exchange rate between two currencies. The service normalizes the currency codes, queries the database for the most recent active rate for the pair, and returns the rate along with its source and effective date.

Steps:

  1. Client sends GetRate(fromCurrency, toCurrency) via SOAP
  2. Service normalizes both currency codes (trim, uppercase, validate 3-letter format)
  3. Service queries CurrencyPairs joined with ExchangeRates for the latest non-expired, active rate
  4. If a rate is found, CurrencyRateData is returned to the client
  5. If no rate exists, a business fault (FaultException) is raised

Workflow 2: Convert Currency Amount

A client requests the converted value of an amount from one currency to another.

Steps:

  1. Client sends ConvertAmount(amount, fromCurrency, toCurrency) via SOAP
  2. Service validates that amount is non-negative
  3. Service delegates to GetRate workflow to retrieve the current rate
  4. Service multiplies amount × rate, rounding to 4 decimal places (MidpointRounding.AwayFromZero)
  5. Converted decimal result is returned to the client

Workflow 3: List Supported Currencies

A client queries the full list of tradeable currency codes available in the system.

Steps:

  1. Client sends GetSupportedCurrencies() via SOAP
  2. Service queries the union of all distinct BaseCurrency and QuoteCurrency values in active CurrencyPairs
  3. Sorted list of unique currency codes is returned as a string[]

Cross-Service Data Flows

ZavaCurrencyService has no inter-service communication. All data originates from a single SQL Server database. Currency pair and rate data is assumed to be populated by an external feed or batch process outside this service; the service is read-only with respect to the database.

Business Rules & Decision Logic

Validation Rules:

  • Currency codes must be non-null, non-whitespace, and exactly 3 characters long; violation raises a FaultException("Currency code must be exactly 3 letters")
  • Conversion amounts must be non-negative; negative amounts raise a FaultException("Amount must be non-negative")
  • Currency codes are normalized (trimmed and uppercased) before any lookup, making input case-insensitive

Decision Logic:

  • Rate resolution selects the most recently effective, non-expired rate (ExpiryDate IS NULL OR ExpiryDate > GETDATE()) ordered by EffectiveDate DESC; only rates on active pairs (IsActive = 1) are eligible
  • If no qualifying rate exists, the service raises a fault rather than returning a default or estimated value

Computed Values:

  • Converted amounts are computed as Round(amount × MidRate, 4, MidpointRounding.AwayFromZero), applying banker's-rounding-avoidance for financial accuracy

Transactions:

  • No explicit transaction management is used; all operations are single read-only queries with no state mutation

Error Handling:

  • All business error conditions are surfaced as WCF FaultException (untyped), which results in a SOAP Fault delivered to the client
  • No dead-letter handling or compensating actions exist (the service is read-only)

Authorization:

  • No authentication or authorization is enforced; all three operations and the health check are accessible by any caller without credentials

Version & Compatibility Risks

All dependencies are .NET Framework 4.8 in-box assemblies with no third-party NuGet packages declared. While .NET Framework 4.8 remains supported by Microsoft, it is in maintenance mode and will not receive new features. System.ServiceModel (WCF) and System.Web (ASP.NET) are not available in .NET Core/.NET 5+; migrating to modern .NET requires replacing WCF with gRPC or ASP.NET Core minimal APIs and removing the System.Web dependency entirely. The System.Data.SqlClient namespace used for database access should be replaced with Microsoft.Data.SqlClient when targeting .NET 6+.

Notable Observations

  • Zero third-party NuGet packages: The service has no external library dependencies, making dependency management trivial but also indicating a very thin application stack reliant on aging framework primitives.
  • WCF (System.ServiceModel) is not portable: WCF server-side hosting is unavailable in .NET Core/.NET 5+. Modernization requires migrating the SOAP contract to a different protocol (REST, gRPC) or using the community CoreWCF library.
  • System.Web dependency: System.Web ties the application to IIS/Windows hosting and is incompatible with .NET Core. The HealthHandler (IHttpHandler) must be rewritten as ASP.NET Core middleware or a minimal API endpoint.
  • No logging framework: The service uses no structured logging library (e.g., Serilog, NLog, Microsoft.Extensions.Logging), which limits observability and cloud-readiness.
